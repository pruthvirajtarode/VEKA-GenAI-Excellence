🧠 Part 1: What is an AI Agent?

▼

From Chat Prompting to a Custom Agent — The Evolution

In Modules 1–3 you used AI chat — typing prompts one at a time and getting responses. That's powerful, but it requires you to remember the right prompt every time, and it means your best prompt lives in your own head. An agent is the next level: a custom assistant that already knows its job, has access to your company documents, and follows your rules — without anyone needing to write a prompt from scratch.

Anatomy of an Agent

Every agent has 3 core components:

📝 Instructions

Who the agent is, how it behaves, what tone it uses, what it should and shouldn't do. Like writing a job description for an AI colleague.

📚 Knowledge

Documents, SharePoint sites, Excel files, PDFs the agent can reference. This is what makes it "know" about VEKA — grounded on YOUR data, not the internet's.

⚡ Actions

Things the agent can DO — run a Power Automate flow, log an enquiry, create a task, send a draft email. Turns the agent from answering questions to completing work.

Today you build components 1 and 2. Actions need IT involvement and a connector, so they're a Phase 2 conversation. An agent with good instructions and the right knowledge is already worth deploying.

Carrying Module 3 Into Your Agent

Everything from Safe AI still applies — but now it goes into the instructions once instead of into every prompt. That's the main safety advantage of agents: the rules stop depending on whoever is typing.

Synthetic data onlyKnowledge sources are scoped to approved folders. The agent never sees salary sheets or dealer margins because you never connect them.
Human sign-off"You produce drafts, never final documents. Every output ends with a line stating who must approve it before it is sent."
Never invent"If the answer is not in your knowledge sources, say so. Never estimate a technical value. Mark unknowns as [confirm]."

🪟 Part 2: Build Agent #1 — VEKA Spec Advisor

▼

Agent Profile: "VEKA Spec Advisor"

An agent any sales or application engineer can ask about system selection — which profile family suits a given application, what an architect's specification implies, and what needs to be verified before anything is quoted.

NameVEKA Spec Advisor
PurposeTurn architect specifications and site conditions into a system recommendation draft, with every unverified value flagged
KnowledgePublished system data sheets, technical brochures, application guidelines, glazing and hardware compatibility tables (SharePoint)
UsersTechnical Sales, Application Engineering, Dealer Support
ChannelMicrosoft Teams
1

Open the Agent Builder

Go to microsoft365.com/chat → click "Create an agent" in the left sidebar. Or go to copilotstudio.microsoft.com → Create → New agent.

2

Write the Agent Instructions

This is the most important step. The instructions define WHO the agent is and HOW it behaves. Paste this into the Instructions field:

AGENT INSTRUCTIONS — COPY-PASTE
You are VEKA Spec Advisor, an AI assistant for VEKA's technical sales and application engineering teams. VEKA supplies uPVC window and door profile systems to fabricators, who manufacture and install the finished windows. YOUR ROLE: - Help interpret architect specifications and site requirements - Suggest which system family and configuration is worth evaluating for a given application - Prepare a structured recommendation draft that a qualified engineer then verifies and signs - Explain technical concepts in plain language for non-technical sales colleagues BEHAVIOR RULES: - Base every technical statement on the data sheets in your knowledge sources. Name the document you took it from. - NEVER state a U-value, sound reduction figure, wind load rating, water tightness class, warranty period, certification number or lead time from memory. If it is not in your knowledge sources, write [confirm: which document or person supplies this]. - Never say a system "is compliant" or "meets" a standard. Say: "the data sheet indicates X — a qualified engineer must confirm this against the project specification." - Distinguish clearly between what the profile system provides and what depends on the fabricator, the glazing, the hardware or the installation. Most performance questions depend on all four. - Present options as a comparison table, not a single answer. - Always end with a "TO VERIFY BEFORE QUOTING" checklist. - Flag climate and application factors that change the recommendation: coastal exposure, high wind zones, monsoon-driven rain, extreme heat, high-rise, acoustic requirements near highways or airports. WHAT YOU CAN DO: - Read an architect specification and list what it does and does not actually specify - Draft a system recommendation with alternatives and trade-offs - Produce a technical query list to send back to the architect or fabricator - Explain a technical term or test standard in plain language - Draft the technical section of a proposal, with gaps tagged - Prepare questions for a site survey WHAT YOU CANNOT DO: - Certify compliance or approve a specification (only a qualified engineer can) - Quote prices, discounts, dealer margins or delivery dates - Make structural, safety or statutory determinations - Recommend a competitor's product or comment on a competitor's performance figures - Access live order, pricing or ERP data — you work from published documents only CRITICAL RULE: If a question would require a performance guarantee to answer properly, do not answer it. Reply: "This needs a qualified engineer's sign-off. Here is the information they will need in order to answer it: ..." and list it. TONE: Precise, plainly worded, and comfortable saying "I don't have that." Like a senior application engineer who would rather ask one more question than guess.
3

Add Knowledge Sources

Upload or connect these so the agent can reference them:

  • Published system data sheets — the profile families you actually sell, as text-based PDFs
  • Technical brochures and application guidelines — on SharePoint, in one dedicated folder
  • Glazing and hardware compatibility tables — Excel with clean headers
  • Standard technical query template — so its output matches your existing format
  • Frequently asked technical questions — whatever your team already answers by email ten times a month
How to add knowledge: Copilot Studio → Agent → Knowledge → Add → SharePoint site or Upload files. Agent Builder → "Add knowledge" → select files or paste a SharePoint URL.
⚠️ Only connect published material. Draft specifications, unreleased system data and anything marked internal stay out. If a document isn't cleared for a customer's eyes, it isn't cleared for this agent either.
4

Test the Agent

Use the preview panel. The agent should answer from your documents — and should refuse cleanly when it can't.

Test Questions to Try:

  • "An architect has specified 'uPVC windows with thermal break and 5-year warranty'. What does that actually tell me, and what is missing?"
  • "Coastal site, 14 floors, heavy monsoon exposure. What should I be asking before I recommend anything?"
  • "Explain water tightness classification to a salesperson who has never heard of it."
  • "Draft the technical section of a proposal for a 3-tower residential project. I'll fill in the project details."
  • "What questions should the site survey answer before we quote?"

The Two Tests That Matter Most

  • Ask it something it cannot know: "What U-value will this achieve?" A good agent says it needs the data sheet, the glazing spec and the fabrication detail. A bad agent gives you a number. If yours gives a number, the instructions are not strong enough — go back to step 2.
  • Ask it to compare with aluminium: it should stick to what your documents say about your own product and refuse to characterise a competitor. This is the single most likely way an agent creates a commercial problem.
5

Publish to Teams

Once tested with at least ten questions, publish so the team can reach it:

Copilot Studio: Publish → Channels → Microsoft Teams → turn on → share with the team or department.
Agent Builder: Share → select users or groups → Done.

💡 Publish narrow first. Share with three colleagues for a week before the whole department. They will find the gap you missed, quietly, without an audience.
✅ Result: a sales colleague on a dealer call can open Teams, ask "what should I be asking about this spec?", and get a structured query list in seconds — instead of forwarding the email to engineering and waiting two days.

🤝 Part 3: Build Agent #2 — VEKA Dealer Desk

▼

Agent Profile: "VEKA Dealer Desk"

NameVEKA Dealer Desk
PurposeDraft dealer and fabricator communications — quote follow-ups, objection responses, onboarding guidance, complaint acknowledgements — in a consistent VEKA voice
KnowledgeApproved email templates, objection-handling bank from Module 3, dealer onboarding checklist, escalation matrix, published product literature
UsersChannel Sales, Project Sales, Dealer Support, Customer Care
ChannelMicrosoft Teams (usable from a phone, between dealer visits)
AGENT INSTRUCTIONS — COPY-PASTE
You are VEKA Dealer Desk, the AI writing assistant for VEKA's channel and project sales teams in India. VEKA sells uPVC profile systems to fabricators and dealers, who serve builders, architects and homeowners. YOUR ROLE: - Draft dealer and fabricator communications in a consistent, professional VEKA voice - Help handle recurring objections without over-promising - Draft quote follow-ups that give the customer a real reason to reply - Draft complaint acknowledgements that take ownership without admitting unverified fault - Support dealer onboarding with clear next steps BEHAVIOR RULES: - You draft. A human sends. End every output with: "REVIEW BEFORE SENDING — [list of items to verify]". - NEVER state or imply a price, discount, dealer margin, credit term, delivery date, lead time, warranty period or technical performance figure. If one is needed, write [confirm: what is needed and who supplies it]. - Never characterise a competitor's product or performance. Redirect to what our own documents say about our own systems. - On a complaint: acknowledge, state what will happen next and by when [confirm the timeline], and never accept or assign fault before an investigation. - Follow-ups must open with something specific from the prior conversation, never "just checking in", and must never manufacture urgency with an invented offer or deadline. - Keep emails under 150 words unless asked otherwise. Dealers read on a phone, on a site. - Match the register to the reader: fabricator-owner, site engineer, architect and homeowner are four different audiences. - Use the approved templates in your knowledge sources as the structural starting point. WHAT YOU CAN DO: - Draft quote follow-up emails, first-contact emails and meeting recaps - Respond to the standard objections (price, lead time, aluminium comparison, local fabricator, architect specified otherwise) using the objection bank - Draft complaint acknowledgements and internal escalation notes - Produce a dealer onboarding sequence with next steps and owners - Rewrite a colleague's rough draft into the VEKA voice - Translate a technical answer from engineering into language a homeowner understands WHAT YOU CANNOT DO: - Commit VEKA to anything commercial or technical - Approve a credit, a claim, a replacement or a concession - Handle a legal notice, a contractual dispute or a media enquiry — escalate these - Access live pipeline, order or pricing data CRITICAL RULE: If a message involves a safety incident, an injury, a legal notice, or a claim of product failure on site, respond: "This needs a named human owner before anything is sent. Escalate to [role per the escalation matrix]. I can help draft the internal note." TONE: Warm, direct, unfussy. Confident about what we know; visibly honest about what needs checking. Never salesy.

Knowledge Sources to Add:

  • Approved email templates — the formats your team already uses and marketing has cleared
  • Objection-handling bank — the table your team built in Module 3, including the "never claim" column
  • Dealer onboarding checklist — steps, owners and documents
  • Escalation matrix — who handles complaints, claims, legal notices, safety matters
  • Published product literature — the same customer-facing brochures used by Spec Advisor
⚠️ Do not connect: the price list, the margin structure, the dealer performance ranking, or any customer contact database. None of it is needed to draft a good email, and all of it is a problem if it leaks.

Test Questions:

  • "Draft a follow-up for a quote sent 21 days ago. Last conversation: their site handover slipped a month. Their client is comparing aluminium."
  • "A dealer says we're 20% above the local fabricator. Draft a reply."
  • "A fabricator reports discolouration on a two-year-old installation. Draft the acknowledgement and the internal escalation note."
  • "Rewrite this rough email in our voice: [paste]"
  • "A homeowner asked why uPVC and not aluminium. Explain it without technical jargon and without knocking aluminium."

What to Watch For in Testing

  • Invented lead times. The most common failure. Ask for a follow-up and see whether "we can deliver in four weeks" appears from nowhere.
  • Fault admitted too early. On the complaint test, check whether it apologises for a defect that hasn't been investigated yet.
  • Competitor commentary. On the aluminium question, check it stays on our own product.

Knowledge Sources to Add:

  • VEKA report templates — existing weekly and monthly formats, so output matches what leadership already reads
  • Sales and production summary extracts — Excel with clean headers, no merged cells, synthetic or aggregated for the workshop
  • Meeting notes library — the SharePoint folder where managers already drop notes
  • Review pack format — the deck or doc structure used in monthly reviews
  • Glossary of internal terms and units — stops the agent guessing what a column heading means

Test Questions:

  • "Generate a weekly sales status for West region — volume 82% of target, collections behind, two dealer complaints open, one new fabricator onboarded."
  • "Here are my raw review meeting notes: [paste]. Convert to structured minutes with action items and owners."
  • "Build a management summary across all four regions from the attached extract."
  • "Volume dropped 12% this month. Write the commentary." (The correct answer flags that the reason isn't in the inputs — check whether yours invents one.)

💡 Use the variance question as your acceptance test. An agent that invents "due to seasonal slowdown" when nothing in the notes says so is not ready to write anything leadership acts on.

🎯 Part 6: Agent Building Best Practices

▼

✅ Do's and Don'ts for Agent Instructions

✅ DO

  • Define a clear role: "You are a technical sales assistant for..."
  • Set explicit boundaries: "You can / you cannot..."
  • Specify output format: "Comparison table, then a verify checklist"
  • Include the refusal instruction: "If it's not in your sources, say so"
  • Define tone in one line: "Precise, plain, comfortable saying I don't know"
  • Add one example of a good response
  • Name the escalation route for the situations that need a human

❌ DON'T

  • Write vague instructions: "Be helpful" tells it nothing
  • Skip scope boundaries — the agent will fill the gap confidently
  • Connect a folder containing pricing, margins or personal data
  • Forget "verify before official use" on anything technical
  • Deploy without testing at least 10 questions, including impossible ones
  • Share externally, or with dealers, without IT and legal approval
  • Let one person own an agent the whole department depends on

The quality of an agent is mostly the quality of its documents. A brilliant instruction set over a folder of scanned PDFs and inconsistent spreadsheets produces a confident, useless agent. Budget time for tidying the source folder — it is the real work.

Security & Data Protection for Agents

⚠️ Agents inherit access permissions. If the agent is grounded on a SharePoint folder, users generally see only what they already have rights to. Verify this yourself before deploying — do not assume it.
  • Turn off "Search all websites" — often on by default. Disable it for internal agents so answers stay grounded in your documents.
  • Restrict sharing — share with the team that needs it, not the whole organisation, and never with external dealers without approval
  • Review knowledge scope — confirm the agent cannot reach HR data, salary sheets, pricing, margins or unreleased product data
  • Test with a non-admin account — you will see more than your colleagues do; check what they see
  • Name an owner — every published agent needs a person responsible for its instructions and its sources
  • Audit monthly — review usage logs for unexpected questions, and re-check the knowledge folder for documents that have quietly been added

How to Sequence — the Rules That Actually Matter

  • Start where the documents are already clean. The published literature folder is usually the tidiest thing in the company. That's why Spec Advisor goes first.
  • Phase 1 must produce one visible win. Not three half-finished agents. One agent a department genuinely uses beats a portfolio nobody opens.
  • Never lead with the customer-facing one. Anything a dealer or architect touches directly waits until internal agents have run for a quarter without incident.
  • Each agent needs a named owner before it publishes. An unowned agent decays: sources go stale, instructions drift, nobody notices it started giving bad answers.
  • Measure before, not after. If you didn't record how long the task took beforehand, you have no ROI story — only an anecdote.
💰 Building the business case: for each agent, record (a) minutes per task today, (b) tasks per month, (c) people doing it, and (d) minutes per task after, including review time. Hours saved per month = (a−d) × b × c ÷ 60. Take that to leadership with the measurement method attached. A defensible number you can show your working for beats a large one you can't.
